# Step 1 — Status substrate (detail plan)

Increment 1 of `docs/notes/0000186F-execution-plan.md`. Task 00001A5D.

**Goal:** the six tables, their Java entities, their repositories and their seed data exist, boot,
and are covered by tests.

**Non-goal:** nothing reads them. No entity gets a status column, no service changes, no template
changes, no API surface. The existing 574 tests must still pass **without modification** — if one
has to change, this step overstepped.

---

## Two open questions — answer before code

### Q1. How do these tables get created in production?

`src/main/resources/application.properties` ships `quarkus.hibernate-orm.database.generation=none`.
The dev sample sets `update`; the test profile sets `drop-and-create`. So in a **packaged
production** run Hibernate creates nothing, and six new entities would reference six missing tables
— failing at first query, not at boot.

Three ways out:

| Option | Means | Cost |
|---|---|---|
| **A (recommended)** | A `StatusSchemaStartup` bean issuing `CREATE TABLE IF NOT EXISTS` for the six tables, mirroring the existing `FavoritesTableStartup` | Raw SQL duplicates the entity mapping; must be kept in sync by hand |
| B | Change the packaged default to `update` | One line, but it silently changes DDL behaviour for **every** table, not just the new ones |
| C | Ship a migration script / document an operator step | Honest, but the project has no migration tool and this is a tracker, not a platform |

Recommendation is **A**, because `FavoritesTableStartup` already establishes the pattern and B's
blast radius is "all tables". But A means two descriptions of the same schema, so it is the owner's
call whether that price is worth it versus just flipping the packaged default.

### Q2. Enum/entity name collision

`pl.perigee.gauge.domain` already contains **enums** named `IssueStatus`, `TasklistStatus`,
`TaskStatus`. ADR 0020 wants **entities** with exactly those names, and says the enums die.

They cannot both live in `domain` — a Java class and an enum cannot share a package and a name.
Deleting the enums now would blow the "no existing test changes" rule of this step.

Proposal: **the status entities live in `pl.perigee.gauge.domain.status`.** Entity names stay
exactly what the owner asked for (`IssueStatus`, not `IssueStatusDefinition`). The enums stay in
`domain` until increment 4 deletes them, at which point imports move from
`domain.IssueStatus` to `domain.status.IssueStatus`.

Alternative: rename the enums now to `IssueStatusSeed` etc. — that is a wide diff today for a
rename that increment 4 performs anyway.

Recommendation: the sub-package. It costs nothing and defers the collision to the increment that
already owns it.

## Files

### Entities — `pl.perigee.gauge.domain.status`

| Class | Table | Notes |
|---|---|---|
| `StatusBase` | — | `@MappedSuperclass`, all six fields, no `@Entity` |
| `ProgressLevel` | `progress_levels` | `name` (unique), `ordinal` — the lookup |
| `AttitudeType` | `attitude_types` | `name` (unique), `ordinal` — the lookup |
| `ProjectStatus` | `project_statuses` | extends `StatusBase` |
| `IssueStatus` | `issue_statuses` | extends `StatusBase` |
| `TasklistStatus` | `tasklist_statuses` | extends `StatusBase` |
| `TaskStatus` | `task_statuses` | extends `StatusBase` |

`StatusBase` fields, with **no** extra properties at any level yet:

```
Integer id          @Id @GeneratedValue(IDENTITY)      // internal, never on the wire
String  code        unique per table, not null
int     precedenceValue  not null, unique per table
String  color
String  progressLevel    not null, by-name reference to progress_levels
String  attitudeType     not null, by-name reference to attitude_types
```

`code` and `precedenceValue` uniqueness are declared as JPA unique constraints so the test profile
(Hibernate `drop-and-create`) enforces them. That is the only place they are enforced — no
application-level duplicate check in this step.

Lookup entities carry `Integer id`, `String name` (unique, not null), `int ordinal` (not null).
Their ids exist only because a table needs a primary key; nothing references them (ADR 0020 §2 —
status rows point at these tables by **name**).

The four status entities are deliberately identical today. They exist separately so a level can
grow properties the others do not have; that is the whole justification and it is not to be
"simplified" into one table later.

### Repositories — `pl.perigee.gauge.repository`

Six thin classes, mirroring `IssueRepository`'s shape (`@ApplicationScoped`, `@Transactional` on
writes): `ProjectStatusRepository`, `IssueStatusRepository`, `TasklistStatusRepository`,
`TaskStatusRepository`, `ProgressLevelRepository`, `AttitudeTypeRepository`.

Minimum surface needed by this step: `listAll()`, `findByCode(String)`, `count()`. Anything a later
increment needs gets added then — an unused method is an untested method.

Rationale for repos rather than raw Panache statics: the owner asked for "a service layer enforcing
database access". Scattering `IssueStatus.list("code", …)` through startup beans is what that
sentence rules out.

### Seeder — `pl.perigee.gauge.config.StatusSeedStartup`

Shape copied from the working precedent in this repo, not the broken one:
`@Startup` + `@ApplicationScoped` + `@PostConstruct` + `QuarkusTransaction.run`
(`AuthStartupBean` / `FavoritesTableStartup`). **Not** `@Observes StartupEvent` + `@Transactional`
— that combination is broken on Quarkus 3.x here (issue 0000055D).

Order inside one transaction: seed the two lookup tables, then the four status tables. Status rows
reference lookup names, so a status inserted before its level exists would be an inconsistent row
even though there is no FK to stop it.

Idempotency rule: insert **only when `findByCode` returns empty**. Never update an existing row —
once seeded, the row belongs to the operator, and a redeploy must not undo a colour change or a
rename. Log one line per table stating how many rows were inserted, so a restart is quiet and a
first boot is visible.

Seed content: exactly the table in ADR 0020 §13 — 2 project, 4 issue, 4 tasklist, 5 task statuses,
6 progress levels, 4 attitudes. Colours copied from the current palette so nothing shifts visually
when increment 5 starts using them.

### Tests — `src/test/java/pl/perigee/gauge/`

`domain/status/StatusSeedTest` (`@QuarkusTest`):

1. Seeding runs and every table has its expected row count (2 / 4 / 4 / 5 / 6 / 4).
2. Codes per level match ADR §13 exactly, including `OPENED`/`CLOSED` for projects.
3. `precedenceValue` is contiguous from 0 and unique per table.
4. Every status's `progressLevel` and `attitudeType` name exists in the corresponding lookup table
   — the integrity check no FK provides.
5. Seeding twice leaves the counts unchanged and does not overwrite an edited row: edit a colour,
   re-run the seeder, assert the edit survived. (This is the actual idempotency requirement.)
6. Lookup ordinals are the fixed values from ADR §3.
7. Status ids are `Integer` and are **not** hex-8 strings; a status id does not appear in the
   `IdProvider` counter's scan — create an entity after seeding and assert its id is `00000001`,
   not influenced by status rows.
8. `code` uniqueness and `precedenceValue` uniqueness are enforced — insert a duplicate and expect
   a persistence exception.

Test isolation: these run in the default profile, which is `drop-and-create`. No `@TestProfile`
needed — nothing here is auth-dependent.

## Risks

- **Schema drift between entity mapping and the DDL bean** — only if Q1 answers A. Mitigation: the
  test profile uses `drop-and-create`, so it exercises the entities, not the SQL. A dedicated test
  that runs the DDL against an empty in-memory database and then queries through the entities is
  worth its keep; add it in step 3 where the real migration rehearsal happens.
- **Seeder ordering vs `IdProvider`** — irrelevant here (int ids), but if the seeder ever starts
  calling `nextId()` it must run after `IdProvider.onStart`. Not applicable to this step.
- **A sixth `@Entity` in a new package that OpenAPI tries to scan** — `StatusBase` is a
  `@MappedSuperclass`, so it is not an entity and must not be added to any exclude list.
