# Step 1 — Status substrate (detail plan)

Increment 1 of `docs/notes/0000186F-execution-plan.md`. Task 00001A5D.

**Goal:** the six tables, their Java entities, their repositories and their seed data exist, boot,
and are covered by tests.

**Non-goal:** nothing reads them. No entity gets a status column, no service changes, no template
changes, no API surface. The existing 574 tests must still pass **without modification** — if one
has to change, this step overstepped.

---

## Decisions (answered before code)

### D1. Hibernate creates the tables: packaged `database.generation` becomes `update`.

Owner, final: *"well, then change the ddl to update. its gonna be easier."*

Three positions were held on this, in order — recorded so nobody re-proposes the middle one:

1. `CREATE TABLE IF NOT EXISTS` bean (agent) — rejected: six hand-written tables are a second
   description of the schema, kept in sync by eye.
2. Startup guard that refuses to boot when a table is missing (owner) — **also dropped**. Once
   Hibernate creates the tables, the guard cannot fire in a correctly deployed instance, and a check
   that cannot fire is dead code.
3. **`quarkus.hibernate-orm.database.generation=update` in `src/main/resources/application.properties`
   (owner, adopted).** One line. The six new tables are created by their entities, like every other
   table.

So in this step there is **no DDL bean and no guard**. Nothing else about the seeder changes.

**`update` is additive only — it never renames.** Worth knowing now, because it does not remove the
need for explicit SQL in increment 3: the existing `status` code column must become `statusCode`
before the new `status` int column can take that name. `update` will happily add `statusCode`, but it
will not rename `status`, and it will not change a `varchar` column into an `int`. Increment 3
therefore still needs raw ALTER statements following the `IssueDescriptionColumnStartup` precedent,
and the ordering of those statements against Hibernate's own schema update must be settled
empirically there — not assumed.

**Test isolation is safe.** `src/test/resources/application.properties` outranks the packaged file and
sets `drop-and-create`, so the suite keeps recreating the schema. The 00001878 leak was caused by a
*root* `application.properties` on the working directory, which is still not allowed.

**Production caveat, stated once.** `update` means a schema mistake shows up as wrong behaviour rather
than a refusal to start. That is the accepted cost of "easier", and it is why the migration in
increment 3 is tested exhaustively rather than trusted.

### D2. Status entities carry a `Def` suffix and live in `pl.perigee.gauge.domain`

Owner, final: *"Simple names suck indeed. add something then :/ maybe 'Def'. 'definition' suffix
suck. but well, its gonna be easier than screwing with bugs."*

So the earlier "plain names + sub-package" plan is dropped — the owner's objection is to the
*ambiguity*, not to the package: two types with the same simple name force fully-qualified references
and aliasing wherever both appear, and that is a bug farm. A suffix is cheaper than a class of bugs.

Names:

| Role | Class |
|---|---|
| mapped superclass | `StatusBase` (unsuffixed — abstract, never named outside the package) |
| lookup | `ProgressLevelDef`, `AttitudeTypeDef` |
| status | `ProjectStatusDef`, `IssueStatusDef`, `TasklistStatusDef`, `TaskStatusDef` |

- All in `pl.perigee.gauge.domain`, **flat**, next to the existing entities. No sub-package: with
  distinct names there is nothing left for it to disambiguate, and one package is the easier route.
- `Def` = *definition*, which is also the honest reading — these rows define what a status is.
- The enums keep their names and stay until **increment 4** deletes them. No enum is renamed in this
  step, so the existing 574 tests still pass unmodified.
- **Dropping the `Def` suffix is a later, optional, mechanical rename** — only ever *after* the enums
  are gone. Do not do it in this step, and do not do it before increment 4.

## Files

### Entities — `pl.perigee.gauge.domain` (flat, per D2)

| Class | Table | Notes |
|---|---|---|
| `StatusBase` | — | `@MappedSuperclass`, all six fields, no `@Entity` |
| `ProgressLevelDef` | `progress_levels` | `name` (unique), `ordinal` — the lookup |
| `AttitudeTypeDef` | `attitude_types` | `name` (unique), `ordinal` — the lookup |
| `ProjectStatusDef` | `project_statuses` | extends `StatusBase` |
| `IssueStatusDef` | `issue_statuses` | extends `StatusBase` |
| `TasklistStatusDef` | `tasklist_statuses` | extends `StatusBase` |
| `TaskStatusDef` | `task_statuses` | extends `StatusBase` |

`StatusBase` fields, with **no** extra properties at any level yet:

```
Integer id          @Id @GeneratedValue(IDENTITY)      // internal, never on the wire
String  code        unique per table, not null
int     precedenceValue  not null, unique per table
String  color
String  progressLevel    not null, by-name reference to progress_levels
String  attitudeType     not null, by-name reference to attitude_types
```

`code` and `precedenceValue` uniqueness are declared as JPA unique constraints so the test profile
(Hibernate `drop-and-create`) enforces them. That is the only place they are enforced — no
application-level duplicate check in this step.

Lookup entities carry `Integer id`, `String name` (unique, not null), `int ordinal` (not null).
Their ids exist only because a table needs a primary key; nothing references them (ADR 0020 §2 —
status rows point at these tables by **name**).

The four status entities are deliberately identical today. They exist separately so a level can
grow properties the others do not have; that is the whole justification and it is not to be
"simplified" into one table later.

### Repositories — `pl.perigee.gauge.repository`

Six thin classes, mirroring `IssueRepository`'s shape (`@ApplicationScoped`, `@Transactional` on
writes): `ProjectStatusRepository`, `IssueStatusRepository`, `TasklistStatusRepository`,
`TaskStatusRepository`, `ProgressLevelRepository`, `AttitudeTypeRepository`.

Repository names are **not** suffixed — nothing collides with them, and `IssueStatusRepository`
operating on `IssueStatusDef` is the ordinary Java reading. The `Def` suffix is on the entity classes
only.

Minimum surface needed by this step: `listAll()`, `findByCode(String)`, `count()`. Anything a later
increment needs gets added then — an unused method is an untested method.

Rationale for repos rather than raw Panache statics: the owner asked for "a service layer enforcing
database access". Scattering `IssueStatus.list("code", …)` through startup beans is what that
sentence rules out.

### Seeder — `pl.perigee.gauge.config.StatusSeedStartup`

Shape copied from the working precedent in this repo, not the broken one:
`@Startup` + `@ApplicationScoped` + `@PostConstruct` + `QuarkusTransaction.run`
(`AuthStartupBean` / `FavoritesTableStartup`). **Not** `@Observes StartupEvent` + `@Transactional`
— that combination is broken on Quarkus 3.x here (issue 0000055D).

No guard, no DDL — Hibernate's `update` has already created the tables by the time this runs (D1). If
it somehow has not, the seeder fails on the first query with a normal Hibernate error, which is
adequate: there is nothing to report that Hibernate's own message does not say better.

Order inside one transaction: seed the two lookup tables, then the four status tables. Status rows
reference lookup names, so a status inserted before its level exists would be an inconsistent row
even though there is no FK to stop it.

Idempotency rule: insert **only when `findByCode` returns empty**. Never update an existing row —
once seeded, the row belongs to the operator, and a redeploy must not undo a colour change or a
rename. Log one line per table stating how many rows were inserted, so a restart is quiet and a
first boot is visible.

Seed content: exactly the table in ADR 0020 §13 — 2 project, 4 issue, 4 tasklist, 5 task statuses,
6 progress levels, 4 attitudes. Colours copied from the current palette so nothing shifts visually
when increment 5 starts using them.

### Tests — `src/test/java/pl/perigee/gauge/`

`domain/StatusSeedTest` (`@QuarkusTest`), eight tests:

1. Seeding runs and every table has its expected row count (2 / 4 / 4 / 5 / 6 / 4).
2. Codes per level match ADR §13 exactly, including `OPENED`/`CLOSED` for projects.
3. `precedenceValue` is contiguous from 0 and unique per table.
4. Every status's `progressLevel` and `attitudeType` name exists in the corresponding lookup table
   — the integrity check no FK provides.
5. Seeding twice leaves the counts unchanged and does not overwrite an edited row: edit a colour,
   re-run the seeder, assert the edit survived. (This is the actual idempotency requirement.)
6. Lookup ordinals are the fixed values from ADR §3.
7. Status ids are `Integer` and are **not** hex-8 strings; a status id does not appear in the
   `IdProvider` counter's scan — create an entity after seeding and assert its id is `00000001`,
   not influenced by status rows.
8. `code` uniqueness and `precedenceValue` uniqueness are enforced — insert a duplicate and expect
   a persistence exception.

Test isolation: these run in the default profile, which is `drop-and-create`. No `@TestProfile`
needed — nothing here is auth-dependent.

## Risks

- **`generation=update` now applies to every table in production, not just the new ones.** It is
  additive, so it cannot drop data, but it can add a column nobody intended if an entity field is
  added carelessly. Accepted: it is one line instead of a second schema description.
- **`update` does not rename or retype, and increment 3 will need both.** The old `status` varchar
  column has to become `statusCode` and a new int `status` column has to appear under that name.
  Explicit ALTERs are therefore still required in increment 3, and their ordering against Hibernate's
  schema update must be settled empirically there. This step must not leave that assumption
  untested — it only has to not make it worse.
- **Seeder ordering vs `IdProvider`** — irrelevant here (int ids), but if the seeder ever starts
  calling `nextId()` it must run after `IdProvider.onStart`. Not applicable to this step.
- **`StatusBase` must not be treated as an entity.** It is a `@MappedSuperclass` and must not be added
  to `mp.openapi.scan.exclude.classes` or to anything else that expects an entity. Six entities exist,
  not seven.
